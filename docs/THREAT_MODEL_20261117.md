# Threat model: free open test, private source (2026-11-17)

Owner decision 2026-11-17: open free play first (an open test), source code stays private on GitHub (`pumpkin-killer-kiroween`), list the game on a platform, sub-agents later through a rotating router over free Gemini accounts with an API quota lock, protections done well. Method: `threat-model-lite` (four questions, STRIDE, every threat gets a mitigation, every MITIGATED threat names a verification, every ACCEPTED threat needs the owner's dated sign-off). The table is checked for form by `tools/threat_lint.py`; it does not check truth, so the verification column names a real test or file.

## What we are working on
- **Browser game**: `index.html` and `js/*.js` served as static files by the owner's Contabo + Coolify behind a Cloudflare tunnel (Tokyo), with a service worker (`sw.js`). Playing against the built-in computer needs no server call.
- **Relay** `scripts/pk_relay.py`: WebSocket rooms (6-character code from a 32-letter alphabet, red and white seats, up to 3 units per team, spectator seat). Only structured JSON messages, no free text between players.
- **MCP bridge** `scripts/mcp_stdio_server.py`: local stdio only, joins a room as a seat for an agent.
- **Agent routing (planned)**: sub-agents over several free Gemini accounts, keys placed by the owner only, cheapest model, quota lock.
- **Repo and release**: private GitHub repository; privacy gate before any public export.
- Trust boundaries: browser to relay (untrusted players), relay to MCP agent (untrusted agent output), agent to model provider (prompt injection, quota), repo to public (privacy gate), static host to browser (service worker cache).

## What this means before the free open test
Open items that should be closed first, in this order: T1 (caps and expiry), T3 (per-address guess limit), T4 (Origin allowlist set in production), T11 (quota lock before any router goes online), T14 and T15 (owner side). T13 waits for the hybrid-room session's report. Items T6 and T7 are accepted in spirit (a friendly game, no money or accounts) but need the owner's dated sign-off to become ACCEPTED.

Not covered: payment, accounts and personal data do not exist in this game; if a sign-in or analytics is added, redo this model.
