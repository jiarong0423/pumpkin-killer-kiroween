# Owner decisions 2026-11-10 (DECIDED, do not reopen): agents, headless web, modular

1. **Everyone who plays brings their own sub-agent.** A player's seat is controlled by that player's own sub-agent (the human can still watch and give orders if the plan allows it, but the default participant is an agent, connected through MCP). The game never supplies a sub-agent for someone; the built-in AI is only the practice opponent.
2. **In principle the game page is HEADLESS.** The game must run and be playable with no visible UI: state in, actions out (a headless page or a state API/MCP server), the canvas and HUD are only a renderer for watching and for the human view. Rules, turn order, physics and damage must not depend on drawing code.
3. **Modular and easy to maintain.** Split rules / state / rendering / input / agents / data into modules with clear interfaces so each can be tested alone (a rules module must run in node without a browser). Plans must give the module boundaries and the migration path from the single index.html.
4. 4 vs 4 is decided (earlier row). Seats = controller models: agent (default), human, built-in AI.
5. Fairness: each agent receives only its own seat's PUBLIC view (the same information a human sees); hidden shield points, exact wind noise and the AI's aiming state stay hidden.
6. **Three ways to play (owner answer to Kiro 75 Q1, 2026-11-10):** a seat can be played (a) by you yourself, in the page or through the Python engine (.py), (b) by your sub-agent through MCP, or (c) by a FRIEND you invite (human multiplayer). All three use the same rules authority, so the rules cannot live only in the page or only in the Python engine; the plan must name ONE rules module and how the page, the Python/MCP host and a friend's browser all talk to it. Friend multiplayer needs a relay between two browsers (planned local/LAN first; any internet hosting or deploy is a separate owner decision and is not started).
7. **Hosting (owner 2026-11-10: "I will put it on my cloud"):** the owner hosts the game page and the relay/host (friend multiplayer, agent seats) on their OWN cloud. So the relay must be a small deployable server (one process, config by environment variables, no secrets in the repo, a health check, a port setting, WebSocket or HTTP long-poll that works behind a reverse proxy), and judges can reach it, which changes Kiro 75 Q6 (a hosted relay is allowed, the local relay stays as the fallback). The main line and Kiro build and test it locally only; any deploy, push or cloud write happens only when the owner says so.
8. **Kiro 75 Q3-Q6 answered (owner 2026-11-10):**
   - Q3 (wind precision / what an agent sees): a sub-agent that enters the game room ALWAYS runs under the same architecture as a human: it operates like a human (same inputs, same public view, same 12 s timer, same wind as the HUD shows) and can NOT bypass the rules. Tests for this ("bypass tests": illegal action, out-of-turn action, hidden-state read, other seat's unit) come later and must be written against this rule.
   - Q4 (other seats' aim, angle and power): HIDDEN, yes.
   - Q5 (human orders to their own agent): FROZEN for now, not before the freeze.
   - Q6 (README / judges): yes; with the owner's cloud the hosted relay is the main path and the local relay the fallback.
   - Hosting confirmed (owner 2026-11-10): **Contabo (Tokyo) with Coolify.** Design for it: a Dockerfile (or Coolify's Nixpacks) per service, config by environment variables set in Coolify, one exposed port per service behind Coolify's reverse proxy (Traefik), WebSocket must work through it, a `/health` route for Coolify's health check, no secrets in the repo, state either in memory or in one mounted volume. Static page and relay can be two services. Not built or deployed yet.
9. **Compute on each player's own device (owner 2026-11-10: "in short, everyone calculates on their own device").** Every player's device (browser, or an agent's own local process) runs the full rules itself; the cloud relay on Contabo/Coolify only forwards small messages (seat actions, the shared seed, results), it does not simulate. So the rules module must be DETERMINISTIC: same seed plus same ordered actions gives the same match on every device (seeded RNG, fixed time step, no wall-clock or Math.random in rules, no float-order surprises between browsers; golden-vector tests). Known tension to design for: if every device holds the full state, hidden information (knight A-B-C points, the built-in AI's noise, an opponent's pending aim) is technically readable on the other device; the plan must say how it is protected (for example commit-then-reveal for hidden points, and an honest note that this is trust-based play between friends and agents, not anti-cheat).
10. **MCP is only a channel (owner 2026-11-10).** MCP carries observations and actions between an agent and ITS OWN device's game; it holds no rules and decides nothing. So the rules authority is the deterministic rules module on each device (item 9), not a Python host and not the MCP server. The Python engine and `scripts/mcp_*.py` become thin adapters or optional headless practice tools; Kiro 75's "shared match host with a per-seat proxy" must be re-read as "a thin per-device channel plus the cloud relay that only forwards messages". Anything in tasks 75/76/77 that makes MCP or Python the authority is superseded by this item.
11. **What the owner's cloud does (owner 2026-11-10: "everyone calculates on their own device; I only provide the asset loading, a random invitation code, and the fixed .py mode"):** exactly three jobs, nothing else: (a) serve the page and the assets (static files); (b) issue and match RANDOM INVITATION CODES so friends can find each other's game (rendezvous, plus forwarding the small action messages if a relay is chosen); (c) the FIXED .py MODE: the Python engine stays as one fixed play mode (headless, for agents and practice), kept in line with the page rules (Kiro 80 did the wall and position alignment). The cloud never simulates a match and never stores match state beyond the code and the live connection. Open design point for the plan: forward actions through a tiny WebSocket relay (simple, works behind NAT) versus peer-to-peer after the code match (needs a signalling step and often a TURN server); recommend the tiny relay.
12. **No concurrency concern (owner 2026-11-10: "basically we will not meet concurrency").** Design for a handful of rooms at once: one process, rooms and invitation codes in memory, no database, no queue, no horizontal scaling, no persistence across restarts. Keep only the cheap safety limits already chosen (message size, rate limit per connection, room expiry, code format). Do not spend plan or build time on load handling.
